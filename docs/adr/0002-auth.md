# ADR 0002 — Authentication with Better Auth

Date: 2026-09-09 · Status: accepted

## Context

Every project built from the template needs email + password sign-up with verified emails, 7-day
sessions, roles, and admin operations (change role, revoke sessions), served by the Hono API and
consumed by the Next.js app on another origin.

## Decision

- `better-auth` 1.7.3 with `prismaAdapter` (Prisma 7 client), `emailAndPassword`
  (`requireEmailVerification: true`), `emailVerification.sendOnSignUp`, session `expiresIn` 7d /
  `updateAge` 1d, the **admin plugin** (roles `admin | member`, `defaultRole: member`,
  `adminRoles: ["admin"]`). Extra profile fields are added through `user.additionalFields`.
  Configured once in `packages/auth` (`createAuth(options)`), instantiated by `apps/api`, mounted at
  `/api/auth/*`.
- **Schema**: Better Auth's `user / session / account / verification` models generated with
  `npx auth generate` and merged into `packages/database/prisma/schema/auth/*.prisma` with the repo
  conventions — snake_case tables (`users`, `sessions`, `accounts`, `verifications`), UUID v7
  primary keys generated by Postgres (`advanced.database.generateId: false`), plus `deleted_at` for
  soft delete. Migration `0001_init`.
- **Role column**: `role String? @default("member")`. Better Auth stores roles as strings; the
  allowed set is `roleSchema` in `@repo/validation`, not a Prisma enum, so both sides agree.
- **Verification mail** is never sent inline: `sendVerificationEmail` is a callback the API
  implements with the outbox (ADR 0004).
- **Cookies / CORS**: dev uses `localhost:3000` → `localhost:4000` (cookies are host-scoped, not
  port-scoped, so they are shared). Production deploys web and api under one parent domain and sets
  `cookieDomain` (`advanced.crossSubDomainCookies`), `trustedOrigins` = the web origin, CORS with
  `credentials: true` on `/api/auth/*` and `/trpc/*`.
- **Rate limit**: `rate-limiter-flexible` (`RateLimiterRedis`) on `/api/auth/sign-in/*`.

## Alternatives

Roll our own sessions (more code, same security burden); Clerk/Supabase (data must stay in our
database, see ADR 0001); Prisma enum for `role` (Better Auth writes strings, would break the admin
plugin's `setRole`).

## Consequences

Auth tables follow Better Auth's field names (only table/column names are mapped). Upgrading Better
Auth means re-running `npx auth generate` and diffing against the schema. Session lookup happens per
request in `apps/api/src/core/context.ts`; the web app only forwards cookies.

## Changes

- **2026-10-05** — Public sign-up is disabled (`emailAndPassword.disableSignUp: true`;
  `POST /api/auth/sign-up/email` answers 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED`). Users are created
  only through the admin plugin's `auth.api.createUser`: called server-side it needs no session,
  over HTTP it needs an admin role, and it rejects a role outside the `roles` map. The web app lost
  `/register` and `register-form`, and `signUpSchema` left `@repo/validation`. Verification is
  unchanged: `createUser` sends no mail, `/send-verification-email` (resend) and `verifyEmail` still
  work; `sendOnSignUp` is now inert but harmless. In practice users come from the seed accounts or
  from an admin session calling `POST /api/auth/admin/create-user` (`authClient.admin.createUser`)
  until a create-user UI exists.
- **2026-10-05** — The role set is the catalog's `super_admin | admin | manager | staff`: the admin
  plugin runs with `defaultRole: "staff"` and `adminRoles: ["super_admin", "admin"]`
  (`ADMIN_ROLES`), `ROLES` in `@repo/validation` and the `roles` map in `@repo/auth/access-control`
  list the same four keys, and `member` is gone. `users.role` becomes `String @default("staff")` NOT
  NULL with the foreign key `users.role → roles.key` (`onDelete: Restrict`, indexed; migration
  `20261005143913_align_users_role_with_roles`, which also backfills existing `member` rows to
  `staff`), so the database refuses a role outside the catalog and `toAuthUser`'s fallback to
  `DEFAULT_ROLE` guards only the session's type. Still a string, not a Prisma enum, for the reason
  above. ADR 0005 explains why the foreign key is now safe and how the migration seeds the four
  rows.
- **2026-10-06** — Password flows run on Better Auth, ported from the legacy d-round-api (JWT +
  bcrypt, AES reset tokens on `users`, plaintext temporary passwords by mail). **Invitation**:
  `user.invite` creates the user with `createUser` and no password (no credential account, so no
  sign-in is possible yet) and calls `requestPasswordReset`; **forgot password** and the admin
  **re-send** (`user.sendPasswordReset`) call the same endpoint. `sendResetPassword` mails through
  the outbox — `account-invitation` while the user has no credential account, `password-reset`
  otherwise, nothing for a deactivated user — a random single-use token valid 1 hour
  (`resetPasswordTokenExpiresIn`); a new request does not invalidate an earlier unexpired link.
  `/request-password-reset` answers known and unknown addresses alike and is rate limited per IP (5
  per 15 minutes). Resetting revokes every session (`revokeSessionsOnPasswordReset`) and marks the
  email verified (`onPasswordReset`): the mailed link proves the mailbox, so the separate
  verification step and the web's `/verify-email` page and resend form are gone, while
  `requireEmailVerification` stays on (a user created with a password but unverified recovers
  through forgot-password). One password policy (`passwordSchema`: 8–128 characters, a letter and a
  digit) is parsed by the forms and enforced by a `hooks.before` middleware on `/reset-password`,
  `/change-password`, `/set-password` and `/admin/set-user-password` (`PASSWORD_POLICY`, Japanese
  message); sign-in never applies it. Sign-in passes `rememberMe` (off: a browser-session cookie)
  instead of the legacy credentials kept in `localStorage`. `changePassword` revokes other sessions.
  Legacy bcrypt hashes are not migrated; a data migration would add a `password.verify` that accepts
  them.
- **2026-10-07** — `users` gains our own name columns `last_name`, `first_name`, `last_name_kana`,
  `first_name_kana` (`lastName`, `firstName`, `lastNameKana`, `firstNameKana`): 姓 / 名 and their
  katakana readings セイ / メイ, which the legacy app kept on the user's `Staff` row. Columns on
  `users` rather than a profile table because every user has a name and Better Auth's `name` stays
  the display name the session and mails use: the user service writes `name` = "姓 名" whenever the
  parts change. Expand only (migration `20261007000000_add_user_name_parts`): the columns are
  nullable, so existing users (and Better Auth itself, which knows only `name`) keep working; the
  forms require all four from now on and the kana must be full-width katakana (`kanaSchema`, the
  legacy rule). A later contract step may make them NOT NULL once every user has them. They are not
  Better Auth `additionalFields`: the service writes them, Better Auth never reads them, and they
  are merged by hand like `deletedAt` (`.claude/rules/migrations.md`).
- **2026-10-08** — The role key `staff` becomes `am` (migration
  `20261008044757_rename_staff_role_to_am`): it is the legacy `EnumUserRole.STAFF`, labelled AM in
  the app, and the key `staff` stays free for a later login role of スタッフ (plan of the staff
  ticket, decision 19). The migration inserts `am`, moves every user and grant from `staff` to it,
  deletes `staff` and makes `am` the column default, so it also succeeds where the new roles seed
  ran first. `ROLES`, `DEFAULT_ROLE`, `assignableRoles`, Better Auth's `roles` map, `ROLE_SEEDS`,
  the `permissions.csv` role column and the seed account (`am@test.com`) follow; grants and labels
  are unchanged. The role set of the 2026-10-05 entry reads `super_admin | admin | manager | am`
  from here on.
