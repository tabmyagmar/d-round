# UI rules (packages/ui + apps/web)

## Where components live

| Kind                                 | Location                                         | Example                                 |
| ------------------------------------ | ------------------------------------------------ | --------------------------------------- |
| shadcn primitives (generated by CLI) | `packages/ui/src/components/`                    | `button.tsx`, `input.tsx`, `dialog.tsx` |
| Composed, reusable components        | `packages/ui/src/components/composed/`           | `StatusBadge`, `DataTable`              |
| Helpers and hooks                    | `packages/ui/src/lib/`, `packages/ui/src/hooks/` | `cn` (`lib/utils.ts`)                   |
| Theme tokens                         | `packages/ui/src/styles/globals.css`             | CSS variables (Tailwind v4)             |
| Page-specific components             | next to the route in `apps/web/app/...`          | `users/user-table.tsx`                  |

`@repo/ui` exports `./components/*`, `./lib/*`, `./hooks/*`, `./globals.css` and
`./postcss.config` (`packages/ui/package.json`). Import as
`import { Button } from "@repo/ui/components/button"`.

## Adding a shadcn component

Run the CLI from `apps/web`: `npx shadcn@latest add <component>`. The aliases in
`apps/web/components.json` point at `@repo/ui/*` (components, lib, hooks) and the css entry at
`packages/ui/src/styles/globals.css`, so the CLI writes into `packages/ui`, not into the app. Do
not hand-copy shadcn source and do not edit generated primitives beyond what shadcn documents
(variants via `cva`).

## Promotion rule

A component starts next to the page that needs it. When a **second** consumer appears, move it to
`packages/ui/src/components/composed/` (named export, no app imports). `packages/ui` never imports
from `apps/*` or from server-only packages (`@repo/database`, `@repo/queue`, `@repo/logger`) —
lint-enforced by `boundaries/dependencies`.

## Theming

Tailwind v4: there is no `tailwind.config`; tokens are CSS variables in
`packages/ui/src/styles/globals.css` (`--background`, `--primary`, ...) that Tailwind reads through
its `@theme` block. Change a colour there, never in a component. `prettier-plugin-tailwindcss`
sorts class names using that stylesheet (`prettier.config.mjs`). Merge classes with `cn()`; no
inline `style` for what Tailwind expresses.

## Server vs client components (`apps/web`)

- Server components by default: pages, layouts, data loading, session lookup.
- `"use client"` only for interactivity or hooks (`useState`, `useTRPC`, forms, event handlers).
  Put the client boundary as low as possible — a small interactive leaf, not the page.
- Only Next.js special files (`page`, `layout`, `loading`, `error`, `not-found`, `route`,
  `proxy.ts`, ...) may default-export; everything else uses named exports (lint-enforced in
  `packages/eslint-config/next.js`).
- Data comes through tRPC (`@trpc/tanstack-react-query`), never from `@repo/database` or
  `@repo/queue`; the web app imports `@repo/api` types only (`AppRouter`).
- Component files may be `PascalCase.tsx` or `kebab-case.tsx` (shadcn output); everything else is
  kebab-case.

## Forms

`react-hook-form` + `zodResolver(schema)` with the schema imported from `@repo/validation` — the
same schema the router validates with. Do not redeclare validation in the component. Field
components come from `packages/ui`; errors render from `formState.errors`.
